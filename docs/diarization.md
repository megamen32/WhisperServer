# Разделение по говорящим

В Web UI включите **Различать говорящих** перед загрузкой или записью.
Результат и скопированный текст будут содержать «Спикер 1», «Спикер 2».
Это различение голосов внутри записи; имена людей и узнавание между записями
не определяются. Обычная транскрипция работает без этой зависимости.

## Установка

```bash
pip install -e '.[diarization]'
```

Примите условия модели
[Community-1](https://huggingface.co/pyannote/speaker-diarization-community-1)
в своём Hugging Face аккаунте. Сохраните токен с доступом на чтение как
`HF_TOKEN` в серверном `.env`; он никогда не передаётся браузеру. При первом
запуске загружаются веса. Без доступа модель не сможет запуститься; ошибка
диаризации не маскируется обычной транскрипцией.

## API

Для OpenAI SDK используйте существующие параметры OpenAI:
`response_format="diarized_json"` включает Community-1,
`chunking_strategy="auto"` выбирает автоматическую обработку. Параметр можно
опустить; локальная автоматическая обработка включена по умолчанию.
Для chunking_strategy поддерживается строка auto; настройка VAD-объектом
из облачного API пока не реализована.
Модель здесь локальная: `whisper-1` использует настроенный ASR alias,
сейчас GigaAM v3. Можно явно выбрать `gigaam-v3`, `tiny` и другие локальные
модели. Облачный `gpt-4o-transcribe-diarize` не является локальной моделью.

```python
import os
from openai import OpenAI

client = OpenAI(base_url="https://whisper.bezrabotnyi.com/v1",
                api_key=os.environ["WHISPER_API_KEY"], timeout=86400)
with open("conversation.mp3", "rb") as audio:
    result = client.audio.transcriptions.create(
        model="whisper-1", file=audio,
        response_format="diarized_json", chunking_strategy="auto")
for segment in result.segments:
    print(segment.speaker, segment.start, segment.end, segment.text)
```

Ответ содержит `text`, `task="transcribe"`, полную `duration` и `segments`
с `id`, `type`, `speaker` (A, B, …), `start`, `end`, `text`.
Для длинных разговоров предпочтителен `stream=True`: читайте события
`event.type == "transcript.text.segment"`. Сервер отправляет SSE keepalive,
пока выполняется глобальное разделение говорящих. При обычном POST таймаут
прокси или клиента может истечь раньше серверного, поэтому используйте стрим.

`POST /transcribe` и `POST /web/transcribe`: query-параметр `diarize=true`.
`POST /v1/audio/transcriptions`: multipart-поле `diarize=true`.
Для временных границ и меток используйте `response_format=verbose_json`.

```bash
curl https://whisper.bezrabotnyi.com/v1/audio/transcriptions \
  -H "Authorization: Bearer $WHISPER_API_KEY" \
  -F file=@conversation.wav -F diarize=true -F response_format=verbose_json
```

`text` сохраняет обычный текст. `speaker_text` содержит подписанные реплики;
`segments[].speaker` — идентификатор `SPEAKER_00` и т. д. либо `null`, если
временная граница не совпала с найденной речью. `speaker_turns` содержит
исходные эксклюзивные интервалы Community-1, `diarization_model` — модель.
При `words=true` нативный API возвращает также `words[].speaker`.
Кэш с говорящими отделён от обычного. NDJSON выдаёт подписанные сегменты;
SSE с diarized_json выдаёт transcript.text.segment с говорящим, временем и текстом;
также сохраняются delta и done-события.
Диаризация всего файла выполняется до выдачи первых сегментов: это не
потоковое узнавание людей в реальном времени.

Whisper и Parakeet разделяют фрагменты по времени слов. GigaAM распознаёт
каждый эксклюзивный интервал отдельно, поскольку не выдаёт время слов.
Одновременную речь нескольких людей такой текст представляет одним
говорящим; шум, короткие реплики и похожие голоса могут давать ошибки.

## Бюджет server-88

Проверено 2026-10-13: работающий `whisperserver.service` имеет MemoryHigh
14 GiB, MemoryMax 16 GiB, swap 0, CPUQuota 800%, TasksMax 768, IOWeight 10.
Они остаются внешней границей для общего ASR и диаризации. До новой реальной
модельной проверки расширение этих лимитов не разрешено.

На CUDA-хосте Community-1 работает на GPU через существующий cudabroker:
модель whisper-community-1 запрашивает 1536 MiB VRAM до загрузки, защищает
аренду контекстом inference(), переносит веса на CPU и освобождает CUDA
перед release и переходом к ASR. Пакеты segmentation/embedding — 1;
PyTorch CPU-потоки — 2. Диаризация имеет приоритет на один выше GigaAM,
чтобы простаивающий собственный ASR мог освободить память для следующего
прохода. Активные чужие модели защищает существующий брокер. Пайплайн
выгружается после каждого файла; новый постоянный процесс не используется.
На хосте без CUDA остаётся CPU-путь. Если CUDA есть, а брокер недоступен,
прямой GPU-запуск не выполняется: возвращается ошибка. GPU SDK закреплён
в optional dependency diarization (cudabroker0.2.1).

Обнаруженный class-level LRU num_frames в WeSpeaker удерживал ~39MiB весов
после GC. Выгрузка очищает эти frame-кэши и снимает ссылку на pipeline.
Реальная проверка двух загрузок/выгрузок25-секундной записи: PASS,9.48s
без времени импорта; peak CUDA allocated119.62MiB/reserved154MiB,
RAM cgroup peak1566273536 байт. После каждой выгрузки GPU-байты модели0;
остаётся исходный процессный cuBLAS-workspace8.125MiB (не накапливается).
Это измерение короткого canary, не обещание времени длинных разговоров.
Общая модельная нагрузка остаётся внутри прежних14/16GiB и CPU8 бюджета.
На момент GPU review свободно >4GiB VRAM и >90GiB RAM, диск126GiB;
проверочный job RAM3/4GiB,swap0,CPU2,tasks128,RuntimeMax120s,IOWeight10.
Задание делит общий бюджет с уже работающим CPU-запросом: сумма RAM<14GiB,
CPU<=4 из8, tasks<768; дополнительный ASR в коротком canary не запускался. Ограничения длительности в
20 минут нет. ffmpeg декодирует весь файл в mono 16 kHz float32 на диск,
через prlimit с пределом файла 2 GiB и timeout 600 секунд; превышение приводит
к ошибке, а не усечению. Исходный и компактный PCM вместе занимают до 4 GiB,
перед запуском требуется этот бюджет плюс 20 GiB свободного резерва. PCM
читается через memmap. При включённом VAD записи длиннее 5 минут проходят
VAD блоками до 302 секунд; тишина удаляется перед единым глобальным проходом
Community-1. Таймкоды возвращаются на исходную шкалу, спикеры не сбрасываются
между блоками. При vad_filter=false тишина сохраняется. Временные файлы
удаляются при успехе и ошибке. Прежние пределы сервиса не повышаются.
Проверено перед изменением: ~132 GiB свободного диска, прежний измеренный
пик Community-1 ~905 MiB. Запрос диаризации ожидает до 24 часов
(WHISPER_DIARIZATION_TIMEOUT_SECONDS), стрим получает keepalive каждые 15 секунд. Дополнительный
дисковый бюджет для весов/зависимостей — 2 GiB; проверить перед первой загрузкой.
Первый короткий реальный запуск достиг ~2,2 GiB и был остановлен systemd-oomd
при MemoryHigh=2 GiB. Для проверочного процесса мягкий лимит пересмотрен
до 3 GiB, жёсткий остаётся 4 GiB, swap 0, CPU 2, tasks 128. На момент
пересмотра доступно ~102 GiB RAM, рабочий Whisper занимает ~3,4 GiB;
повышение мягкого лимита не расширяет предел сервиса или GPU. Дополнительно
размер обоих пакетов снижен до 1. Повторный consumer canary прошёл.

После снижения пакетов реальная запись 25,04 секунды с двумя разными
голосами и возвратом первого обработана за 28,13 секунды; memory.peak
проверочного cgroup — 948547584 байт (~905 MiB). Автоматически определены
два спикера; принудительное число говорящих не задавалось.

Браузерная приёмка на server-88 использует тот же установленный AgentBrowser
с отдельной именованной сессией внутри конечного project cgroup:
MemoryHigh/Max 1/2 GiB, swap 0, CPU 200%, TasksMax 128, RuntimeMaxSec 180.
Один браузер и одна вкладка, только собственный тестовый профиль и файл.
CPU affinity ограничена одним доступным CPU для новых проверок (прежняя
приёмка использовала два); Tokio/Rayon — 2 потока,
renderer/raster — 1. Это удерживает браузер в исходном tasks-лимите без
его повышения; финальная реальная приёмка и чтение clipboard прошли.
После проверки закрывается только эта сессия и её unit. Общий MCP host service
не имеет конечных лимитов, поэтому браузер не оставляется внутри него.

Первичная установка: отдельный ограниченный job, RAM soft/hard 1/2 GiB,
swap 0, CPU 2, tasks 128, срок 120 секунд; действующие torch/torchaudio/protobuf
не заменяются. Проверки кода: RAM soft/hard 2/4 GiB, swap 0, CPU 2, tasks 128,
один pytest runner; обычный релиз имеет общий deadline 180 секунд.
Первая проверка модели — один короткий диалог, без параллельных запусков,
с измерением MemoryPeak в конечном cgroup. Длинные проверки относятся к nightly.
