# Разделение по говорящим

В Web UI включите **Различать говорящих** перед загрузкой или записью.
Результат и скопированный текст будут содержать «Спикер 1», «Спикер 2».
Это различение голосов внутри записи; имена людей и узнавание между записями
не определяются. Обычная транскрипция работает без этой зависимости.

## Установка

```bash
pip install -e '.[diarization]'
```

Примите условия модели
[Community-1](https://huggingface.co/pyannote/speaker-diarization-community-1)
в своём Hugging Face аккаунте. Сохраните токен с доступом на чтение как
`HF_TOKEN` в серверном `.env`; он никогда не передаётся браузеру. При первом
запуске загружаются веса. Без доступа модель не сможет запуститься; ошибка
диаризации не маскируется обычной транскрипцией.

## API

`POST /transcribe` и `POST /web/transcribe`: query-параметр `diarize=true`.
`POST /v1/audio/transcriptions`: multipart-поле `diarize=true`.
Для временных границ и меток используйте `response_format=verbose_json`.

```bash
curl https://whisper.bezrabotnyi.com/v1/audio/transcriptions \
  -H "Authorization: Bearer $WHISPER_API_KEY" \
  -F file=@conversation.wav -F diarize=true -F response_format=verbose_json
```

`text` сохраняет обычный текст. `speaker_text` содержит подписанные реплики;
`segments[].speaker` — идентификатор `SPEAKER_00` и т. д. либо `null`, если
временная граница не совпала с найденной речью. `speaker_turns` содержит
исходные эксклюзивные интервалы Community-1, `diarization_model` — модель.
При `words=true` нативный API возвращает также `words[].speaker`.
Кэш с говорящими отделён от обычного. NDJSON выдаёт подписанные сегменты;
SSE OpenAI выдаёт обычные текстовые delta и данные говорящих в done-событии.
Диаризация всего файла выполняется до выдачи первых сегментов: это не
потоковое узнавание людей в реальном времени.

Whisper и Parakeet разделяют фрагменты по времени слов. GigaAM распознаёт
каждый эксклюзивный интервал отдельно, поскольку не выдаёт время слов.
Одновременную речь нескольких людей такой текст представляет одним
говорящим; шум, короткие реплики и похожие голоса могут давать ошибки.

## Бюджет server-88

Проверено 2026-10-13: работающий `whisperserver.service` имеет MemoryHigh
14 GiB, MemoryMax 16 GiB, swap 0, CPUQuota 800%, TasksMax 768, IOWeight 10.
Они остаются внешней границей для общего ASR и диаризации. До новой реальной
модельной проверки расширение этих лимитов не разрешено.

Community-1 работает только на CPU, двумя PyTorch потоками, одним заданием
и с пакетами segmentation/embedding по одному фрагменту.
в существующем последовательном worker. Pipeline освобождается после запроса;
GPU и новый постоянный процесс не используются. Длина ограничена 1200 секунд,
ffmpeg декодирует максимум 1201 секунду mono 16 kHz float32 (~77 MB), timeout
декодирования 60 секунд. Временный файл удаляется worker. Дополнительный
дисковый бюджет для весов/зависимостей — 2 GiB; проверить перед первой загрузкой.
Первый короткий реальный запуск достиг ~2,2 GiB и был остановлен systemd-oomd
при MemoryHigh=2 GiB. Для проверочного процесса мягкий лимит пересмотрен
до 3 GiB, жёсткий остаётся 4 GiB, swap 0, CPU 2, tasks 128. На момент
пересмотра доступно ~102 GiB RAM, рабочий Whisper занимает ~3,4 GiB;
повышение мягкого лимита не расширяет предел сервиса или GPU. Дополнительно
размер обоих пакетов снижен до 1. Требуется повторный consumer canary.

После снижения пакетов реальная запись 25,04 секунды с двумя разными
голосами и возвратом первого обработана за 28,13 секунды; memory.peak
проверочного cgroup — 948547584 байт (~905 MiB). Автоматически определены
два спикера; принудительное число говорящих не задавалось.

Браузерная приёмка на server-88 использует тот же установленный AgentBrowser
с отдельной именованной сессией внутри конечного project cgroup:
MemoryHigh/Max 1/2 GiB, swap 0, CPU 200%, TasksMax 128, RuntimeMaxSec 180.
Один браузер и одна вкладка, только собственный тестовый профиль и файл.
После проверки закрывается только эта сессия и её unit. Общий MCP host service
не имеет конечных лимитов, поэтому браузер не оставляется внутри него.

Первичная установка: отдельный ограниченный job, RAM soft/hard 1/2 GiB,
swap 0, CPU 2, tasks 128, срок 120 секунд; действующие torch/torchaudio/protobuf
не заменяются. Проверки кода: RAM soft/hard 2/4 GiB, swap 0, CPU 2, tasks 128,
один pytest runner; обычный релиз имеет общий deadline 180 секунд.
Первая проверка модели — один короткий диалог, без параллельных запусков,
с измерением MemoryPeak в конечном cgroup. Длинные проверки относятся к nightly.
